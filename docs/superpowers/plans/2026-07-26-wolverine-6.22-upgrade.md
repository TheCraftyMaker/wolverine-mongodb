# WolverineFx 6.22.0 Upgrade Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. The companion prompts file is `docs/superpowers/plans/2026-07-26-wolverine-6.22-upgrade-prompts.md`.

> **Origin (2026-07-26, package-version unification session).** A session scoped to *"one version per package across both solutions"* bumped `WolverineFx` from 6.17.3 to the then-latest 6.22.0 and hit a **new upstream compliance failure**: `DeadLetterAdminCompliance.query_by_replayable_flag`. Investigation established that 6.22.0 added a `bool? Replayable` filter to `DeadLetterEnvelopeQuery` (commit `e63dc8b4a`, 2026-07-21, upstream PRs #3567/#3569) which this provider's `DlqFilter` silently ignores — so `QueryAsync`/`DiscardAsync`/`ReplayAsync` act on the **whole** dead-letter queue when a caller asks for only the replayable (or only the stuck) envelopes. A one-line prototype fix was written, **verified green (182/182 single-node on net9.0 and net10.0)**, and then **deliberately reverted**: the version-unification session's scope was package pins and `Microsoft.SourceLink.GitHub`, not a behavior fix. That session instead pinned `WolverineFx`/the `external/wolverine` submodule at **6.21.0 / V6.21.0** — the last release *before* the new filter — and deferred the real work to this plan.

**Goal:** Move `Wolverine.MongoDB` from WolverineFx 6.21.0 to 6.22.0 with the full compliance suite green on net9.0 and net10.0 (single-node **and** multinode), implementing the `DeadLetterEnvelopeQuery.Replayable` filter server-side as a real behavior fix with a red-first test, and making an explicit, documented decision about every other 6.22.0 surface change (the `IMessageStoreAdmin.MigrateAsync(AutoCreate?)` overload and the two new compliance suites) rather than discovering them later under time pressure.

**Architecture:** Three mechanisms, only the first of which is blocking. **(1) Dead-letter query filter (blocking).** All three query-shaped `IDeadLetters` operations funnel through one private `DlqFilter(DeadLetterEnvelopeQuery)` builder, and the document type already persists the flag as `[BsonElement("replayable")] bool Replayable`. Honouring the new nullable filter is therefore a single translated predicate in a single method — and because `QueryAsync` derives `TotalCount` from `CountDocumentsAsync(filter)`, doing it server-side is the *only* way to keep the count coherent with the page (the compliance fact asserts exactly that). **(2) Admin migration override (decision, likely no-op).** `MigrateAsync(AutoCreate?)` arrived as a **default interface method**, so it is source- and binary-compatible; the task is to decide whether this provider's `AutoCreate`-independent `MigrateAsync()` needs the override at all, and to record the answer. **(3) New optional compliance surface (triage).** 6.22.0 adds `ClearAllWolverineStorageCompliance` and `ExclusiveListenerRecoveryCompliance`; both are subclassed only by the RDBMS-family and Marten providers, and the latter is adjacent to this library's documented **durable-listeners non-goal**. The task is a defensible written triage, not automatic adoption.

**Tech Stack:** .NET 9/10, MongoDB.Driver 3.10.0, WolverineFx 6.21.0 → **6.22.0** (pinned `external/wolverine` submodule moves V6.21.0 → V6.22.0), xUnit + Shouldly (library) / FluentAssertions (demo), Testcontainers.MongoDb (replica set).

**PREREQUISITE: the version-unification PR (branch `chore/unify-package-versions`) is merged to `main`.** That PR leaves `main` at `WolverineFx [6.21.0,7.0.0)` (library range floor), `6.21.0` exact in `demo/Directory.Packages.props`, the submodule at `V6.21.0`, and `MongoDB.Driver [3.10.0,4.0.0)` / `3.10.0`. It also removed the explicit `Microsoft.SourceLink.GitHub` `PackageReference`. **Do not start W2 before it merges** — W2 rewrites the same four files.

## Verified API Facts (established 2026-07-26 against the `external/wolverine` submodule — do NOT re-derive or invent)

Every fact below was read from the submodule at the named tag. Implementing sessions should *confirm* each with a one-line `git show`/grep, not reinvent it. **If a fact does not hold, stop and report — do not improvise.**

**The new filter (upstream):**
- `DeadLetterEnvelopeQuery.Replayable` — `external/wolverine/src/Wolverine/Persistence/Durability/DeadLetterManagement/DeadLetterEnvelopeQuery.cs` (added V6.22.0). Contract from its XML doc: `null` (default) = no filtering, `true` = only envelopes already marked for replay, `false` = only envelopes not yet marked replayable.
- Introduced by commit `e63dc8b4a` "feat(dead-letters): add Replayable filter to DeadLetterEnvelopeQuery (#3567) (#3569)", dated **2026-07-21**. `git tag --contains e63dc8b4a` returns **exactly `V6.22.0`** — so **V6.21.0 is the last release without it**, which is why `main` is pinned there.
- The sibling DTO `DeadLetterEnvelopeGetRequest` (`DeadLetterEnvelopeResults.cs`) gained the same `bool? Replayable`, and **core does the mapping**: `Replayable = request.Replayable` at `external/wolverine/src/Wolverine/Persistence/MessageStoreCollection.cs:470`. **Consequence: the provider has exactly one place to change** — nothing extra is owed for the HTTP/admin request path.

**The failing fact:**
- `DeadLetterAdminCompliance.query_by_replayable_flag` — `external/wolverine/src/Testing/Wolverine.ComplianceTests/DeadLetterAdminCompliance.cs:530-581`. It loads 9 `BadImageFormatException` + 6 `DivideByZeroException` dead letters, calls `ReplayAsync` scoped to the `BadImageFormatException` partition, then asserts: `Replayable = true` → `TotalCount == 9` **and** `Envelopes.Count == 9`; `Replayable = false` → `6`/`6`; default (`null`) → `15`/`15`; and `{ Replayable = false, ExceptionType = BadImageFormatException }` → `0`/`0` (the predicate **composes** with the other filters). The suite's own comment states the intent: server-side, "including a coherent TotalCount, which in-memory filtering cannot give".
- This provider runs that suite: `src/Wolverine.MongoDB.Tests/dead_letter_admin_compliance.cs:11` — `public class dead_letter_admin_compliance : DeadLetterAdminCompliance`. So the new fact is picked up automatically by the version bump; it is not opt-in.

**Local code (the single defect site):**
- `DlqFilter(DeadLetterEnvelopeQuery)` — `src/Wolverine.MongoDB/Internals/MongoDbMessageStore.DeadLetters.cs:13-26`. Translates `MessageIds`, `Range.From`/`Range.To`, `ExceptionType`, `ExceptionMessage` (prefix regex), `MessageType`, `ReceivedAt`. **No `Replayable` clause.**
- Three call sites, all of them: `QueryAsync` (`:60`, with `TotalCount` from `CountDocumentsAsync(filter)` at `:61`), `DiscardAsync` (`:80`, `DeleteManyAsync`), `ReplayAsync` (`:83`, `UpdateManyAsync … Set(x => x.Replayable, true)`). One fix covers all three.
- The flag is already persisted and already round-trips: `[BsonElement("replayable")] public bool Replayable { get; set; }` (`src/Wolverine.MongoDB/Internals/DeadLetterMessage.cs:59`), passed into `DeadLetterEnvelope` by `ToEnvelope()` (`:75`). **No document-shape or index-schema change is required for correctness**; see D3 for the optional index question.
- **The prototype that was proven and reverted** was exactly one line, placed after the `ReceivedAt` clause:
  `if (query.Replayable.HasValue) filter &= b.Eq(x => x.Replayable, query.Replayable.Value);`
  Measured on 6.22.0 in the origin session: **182 passed / 0 failed on net9.0 and net10.0** (`Category!=multinode`). The multinode leg was **started but never completed** on 6.22.0 — W2 owes that run.

**Sibling reference implementations (all four ship it in V6.22.0; this provider is the only one that doesn't, because it lives out-of-tree):**
- RDBMS: `src/Persistence/Wolverine.RDBMS/MessageDatabase.DeadLetterAdminService.cs:166-170` (`and replayable = @p`), inside `writeDeadLetterWhereClause`.
- Oracle: `src/Persistence/Oracle/Wolverine.Oracle/OracleMessageStore.DeadLetters.cs:253-256` (note the `NUMBER(1)` bool coercion — a storage detail with no MongoDB analogue).
- CosmosDb: `src/Persistence/Wolverine.CosmosDb/Internals/CosmosDbMessageStore.DeadLetters.cs:139` (paged query + count), `:290` (`LoadDeadLettersByQuery`), `:346` (parameter binding) — Cosmos needs three sites because it hand-builds two SQL strings; this provider needs one because `DlqFilter` is shared.
- RavenDb: `src/Persistence/Wolverine.RavenDb/Internals/RavenDbMessageStore.DeadLetters.cs:117-119` and `:241-243`.

**Adjacent behavior difference (feeds D1):**
- RDBMS **composes** `MessageIds` with every other predicate (`writeMessageIdArrayQueryList` is appended *after* the `Replayable` clause, `MessageDatabase.DeadLetterAdminService.cs:172-175`).
- This provider **short-circuits**: `if (query.MessageIds is { Length: > 0 }) return b.In(x => x.Id, query.MessageIds);` (`DeadLetters.cs:17`) — an id-list query ignores `Range`, `ExceptionType`, *and* (after the fix) `Replayable`. No upstream fact combines `MessageIds` with another filter, so this is **not** what the new fact catches. D1 decides it explicitly instead of leaving it undocumented.

**Other 6.22.0 surface changes (each needs a decision, none is known-blocking):**

## Lead Open Design Decisions (resolved in W1/W2 — they shape the diff)

**D1 — `MessageIds` short-circuit: compose or keep?** Today an id-list query returns early and ignores every other predicate (`DeadLetters.cs:17`), whereas RDBMS ANDs them. Options: **(A) keep the short-circuit** (zero behavior change beyond the new filter; "fetch these specific ids" is arguably an intentional escape hatch, and no compliance fact contradicts it) — *recommended for this plan's scope*, with a code comment stating the choice; **(B) compose** `MessageIds` with the rest for RDBMS parity (behavior change: an existing caller passing ids **plus** a stale `Range`/`ExceptionType` would start getting fewer rows — semver-relevant on a 1.0.0 library). Whichever is chosen, W2 records it in the method and in the PR body. Do **not** silently change it while adding the `Replayable` clause.

**D2 — Bump and fix in one PR, or two?** **Recommended: one PR (W2).** The red test *is* the upstream fact, and the fact only exists at 6.22.0 — so a "fix first on 6.21.0" PR would have no way to go red, violating this repo's red-first rule. The PR therefore does: submodule → `V6.22.0`, package pins → 6.22.0 in both `Directory.Packages.props`, run the suite to **prove `query_by_replayable_flag` fails**, apply the filter, prove green. The alternative (bump in one PR with the fact known-failing, fix in a second) leaves `main` red and is rejected.

**D3 — Index for `replayable`?** DLQ admin queries can now filter on the flag, and `EnsureIndexesAsync` (`src/Wolverine.MongoDB/Internals/MongoDbMessageStore.Admin.cs:18-64`) already defines compound indexes for other DLQ access paths. Options: **(A) no new index** (recommended — the DLQ is an operator-facing, low-cardinality-by-design collection; the flag is a two-value field and a poor leading key, and adding an index re-raises the documented "`EnsureIndexesAsync` never drops superseded indexes" migration wrinkle); **(B) extend an existing compound index** with `replayable` as a trailing key if W1 finds a sibling provider indexes it. W1 checks whether any sibling adds an index for this column and reports; the default is A.

**D4 — CHANGELOG framing.** The `Replayable` gap is a **bug fix** in a shipped 1.0.0 surface (a filter the caller passes is ignored → wrong rows acted on by `DiscardAsync`/`ReplayAsync`), so it belongs under `### Fixed` with the patch-level reading. The version bump itself stays under `### Changed`. W2 writes both, and **removes the "6.21.0, not the latest 6.22.0" deferral note** the unification PR left in the `### Changed` entry (it points at this plan and becomes false the moment W2 merges).
